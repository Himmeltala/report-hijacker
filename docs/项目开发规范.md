# 项目开发规范

本应用为周报日报 Electron 应用。按本规范生成代码，不添加额外说明。所有页面和组件保持视觉一致。

本规范由以下三部分组成：

1. **代码开发规范** — 样式、布局、组件、文件组织、Electron IPC、状态管理、工具函数、类型定义、配置文件、持久化方案
2. **数据源与业务字段说明** — 任务数据模型、本地/远程字段、业务派生字段、统计口径、同步流程
3. **周报模板插值说明** — xlsx 模板占位符语法、任务行、合计行、模板示例与使用说明

#### 5.3 API 客户端

```ts
function createApiClient() {
  const baseUrl = () => settings.get('connection.apiBaseUrl').trim().replace(/\/+$/, '')
  return {
    async get<T>(path: string, cookie: string): Promise<T> {
      const res = await fetch(`${baseUrl()}${path}`, {
        headers: { Cookie: cookie, 'X-Requested-With': 'XMLHttpRequest' },
      })
      if (!res.ok) throw new Error(`HTTP ${res.status}`)
      return res.json()
    },
    async post<T>(path: string, cookie: string, body?: any): Promise<T> {
      const res = await fetch(`${baseUrl()}${path}`, {
        method: 'POST',
        headers: { Cookie: cookie, 'X-Requested-With': 'XMLHttpRequest', 'Content-Type': 'application/json' },
        body: body !== undefined ? JSON.stringify(body) : undefined,
      })
      if (!res.ok) throw new Error(`HTTP ${res.status}`)
      const text = await res.text()
      return text ? JSON.parse(text) : (null as T)
    },
  }
}
```

### 6 状态管理 (Pinia)

Composition API 风格：

```ts
export const useSettingsStore = defineStore('settings', () => {
  const config = ref<AppConfig>({ ... })
  function updateConfig(partial: Partial<AppConfig>) {
    config.value = { ...config.value, ...partial }
    for (const [key, value] of Object.entries(partial)) {
      const cloned = JSON.parse(JSON.stringify(value))
      window.electronAPI?.setSetting?.(SETTING_KEY_MAP[key as keyof AppConfig] || key, cloned)
    }
  }
  return { config, updateConfig }
})
```

- Store 只管理数据，不操作 UI/路由。跨 Store 用 `useXxxStore()` 获取。
- 配置型 Store 用 `SETTING_KEY_MAP` 映射前端属性名 ↔ 持久化键名
- `loadConfig()` 在 `app.mount()` 前调用

#### 9.4 可配置化原则

新功能先问：**这个值在不同用户/场景会不会不一样？**

- 会 → 做配置项
- 不会但将来可能 → 做配置项（减少后续改代码）
- 常量选型、架构决策、安全开关 → 不做配置项

添加步骤：schema 加定义 → `AppConfig` 加类型 → `SETTING_KEY_MAP` 加映射 → 代码中 `useSettingsStore().config.xxx` 取值 → SettingsDialog 确认 UI

### 10 持久化方案

所有持久化数据存储在 Electron 的 `userData` 目录下，先按用户档案分目录，档案目录内再按职责划分为三个区域。

#### 10.1 目录结构

```
userData/
├── profiles.json              档案名称列表
├── active-profile.json        当前激活的档案名
└── profiles/
    └── <档案名>/               每个档案一套独立数据，首次启动创建「默认用户」
        ├── settings.json      用户配置（Cookie、校验参数、主题等）
        ├── history/           历史任务数据，按日期存储
        │   ├── 2026-07-24.json
        │   └── 2026-07-23.json
        └── store/             通用数据存储（运行时产生的非配置型数据）
            ├── lastBackupTime.json
            └── lastAutoSyncTime.json
```

档案的新建、重命名、删除、切换走 `profile:*` IPC；目录不存在时由 `ensureProfileDir` 自动创建。

#### 10.2 三类数据的区分

| 区域     | 目录/文件                              | 管理方式                                           | 适用场景                                                 |
| -------- | -------------------------------------- | -------------------------------------------------- | -------------------------------------------------------- |
| 配置     | `userData/profiles/<档案>/settings.json` | `AppSettings` 类，通过 `settings:get/set` IPC 读写 | 用户可配置的参数，结构由 `settings_schema.json` 定义     |
| 历史     | `userData/profiles/<档案>/history/*.json` | 独立 IPC 接口 `history:*`                          | 按日期组织的任务历史记录                                 |
| 通用存储 | `userData/profiles/<档案>/store/*.json`   | `store:get/set/delete/keys` IPC 读写               | 运行时产生的非配置型数据（如上次同步时间、上次备份时间） |

#### 10.3 判断准则

新增持久化需求时，按以下顺序判断：

1. **是否为用户可配置的参数？** → 写入 `settings`（在 `settings_schema.json` 中注册）
2. **是否为按日期组织的任务数据？** → 写入 `history`
3. **以上都不是，但需要重启后保留？** → 写入 `store`

#### 10.4 通用存储 (store) 用法

主进程提供四个 IPC 接口：

```ts
// 读取，不存在返回 null
const value = await window.electronAPI.storeGet('myKey')

// 写入，key 作为文件名（myKey.json）
await window.electronAPI.storeSet('myKey', { foo: 123 })

// 删除
await window.electronAPI.storeDelete('myKey')

// 列出所有已存储的 key
const keys = await window.electronAPI.storeKeys()
```

存储目录通过 `getStoreDir()` 获取（`userData/profiles/<档案>/store/`），不存在时自动创建。

#### 10.5 不推荐的方案

- **localStorage**：仅渲染进程可访问、容量有限（5-10MB）、无法原子写入、易被清除，不适用于本项目。
- **Electron 的 session storage**：与渲染进程绑定，重启即丢失。

#### 10.6 内存缓存（非持久化）

`src/utils/cache.ts` 提供基于 `Map` 的 TTL 缓存，用于临时数据（如 API 响应缓存）。默认 TTL 30 分钟，应用重启后丢失。不涉及磁盘写入，不属于持久化范畴。

## 二、数据源与业务字段说明

### 数据来源

任务数据有两个来源：**文本解析**（本地）和 **OpenProject API**（远程）。

| 来源            | 说明                   | 存储位置                      |
| --------------- | ---------------------- | ----------------------------- |
| 文本解析        | 从用户粘贴的文本中提取 | `HistoryTaskItem` 顶层字段    |
| OpenProject API | 同步时从管理平台拉取   | `HistoryTaskItem.remote` 对象 |

同步时，远程数据整体覆盖到 `remote` 字段，业务字段基于 `remote` 实时计算。

### 本地字段（文本解析）

从原始文本直接解析，存储在任务对象顶层。

| 字段             | 说明             | 示例                                             |
| ---------------- | ---------------- | ------------------------------------------------ |
| `seq`            | 序号             | `1`                                              |
| `projectName`    | 项目名称         | `XX项目`                                         |
| `title`          | 任务标题         | `完成登录功能`                                   |
| `handler`        | 处理人           | `张三`                                         |
| `url`            | 任务链接         | `https://xmgl.cdrunnet.com/work_packages/80113`  |
| `score`          | 任务链接预估时长 | `8`                                              |
| `estimatedHours` | 自评预估工时     | `4`                                              |
| `raw`            | 原始文本行       | `1.XX项目-【完成登录-张三】 https://... 【8】` |

### 远程字段（`remote` 对象）

同步时从 OpenProject API 获取的完整响应，整体存储在 `remote` 字段中。

| 字段路径                | 说明                 | 示例                          |
| ----------------------- | -------------------- | ----------------------------- |
| `remote.subject`        | 任务标题             | `根据UI规范修改系统样式-前端` |
| `remote.startDate`      | 开始日期             | `2026-07-16`                  |
| `remote.dueDate`        | 截止日期             | `2026-07-16`                  |
| `remote.estimatedTime`  | 预估时间（ISO 8601） | `PT6H`                        |
| `remote.duration`       | 工期（ISO 8601）     | `P5D`                         |
| `remote.percentageDone` | 完成百分比           | `0`                           |

### 同步流程

```
用户点击同步
    1. 调用 API 获取 remote 数据
    2. 直接覆盖本地字段：
       - title ← remote.subject
       - projectName ← remote._embedded.project.name
       - remote ← 完整 API 响应
    3. 保存到本地 JSON
    4. 业务字段自动重新计算（基于新 remote）
```

同步不涉及差异比较，始终以远程数据为准。

### 使用说明

1. **循环行识别**：包含 `{{task.` 的行会被识别为循环行，自动按任务数量复制
2. **非循环行**：不包含 `{{task.` 的行保持原样，只做全局变量替换
3. **合计行**：使用 `{{summary.}}` 的行作为汇总行，自动对循环区对应列求和
4. **空值处理**：API 字段获取失败时输出空字符串，不影响其他字段
5. **格式保留**：替换只修改单元格值，模板中的样式、边框、合并单元格等格式全部保留
6. **字段优先级**：`task.projectName` 取自解析文本，`task.project` 取自 API，两者可能不同
7. **自定义字段编号**：`customField1`、`customField105`、`customField107` 等编号对应 OpenProject 后台配置，修改编号需同步更新模板
